3. **Tool design.** Pick two tools with overlapping inputs. How do the descriptions prevent misrouting? What did a structured tool error let the agent do that a generic string would not?
   →  route_to_adjuster and escalate_to_human both end a claim, so their inputs overlap, but the descriptions separate them by what each takes: route_to_adjuster takes a "two-to-three sentence summary the adjuster will read first", while escalate_to_human takes a fixed reason (unresolved_ambiguity | low_confidence | missing_facts | policy_dispute | other). Similarly, lookup_policy ("use this early ... to confirm the policy exists, what is covered, and the deductible") takes only a policy_id, while record_claim_fact ("call once per fact") takes a snake_case field and a short value, so the model does not mix up looking up a policy and recording a fact. In claims_intake/tools.py, errors come back through _err(category, retryable, message) as {"is_error": true, ...}. Permanent errors carry retryable=False and name the fix, for example "classify_claim must be called before routing", "assess_severity must be called before routing" and "terminal tool already called this claim". Unexpected exceptions return a "transient" category with retryable=True. This lets the agent retry only a transient failure, run the missing prerequisite tool after a "must be called before routing" error, and avoid a second terminal call, none of which a generic "error" string would tell it.

### System 4 — Orchestration

11. **Push work down.** Defects the SQL query returned vs warm-tier total. Name the indexed query. Why does the model never see the full history?
    → The warm tier (data/warm.sqlite, table defects) held 40 defects after I loaded fixtures/defects.json. The query is WarmStore.defects_since in shift_monitor/warm.py: SELECT * FROM defects WHERE ts > ? ORDER BY ts DESC LIMIT ?, default limit 50, backed by the index idx_defects_ts on defects(ts) (idx_defects_shift_ts on shift, ts also exists). The filtering and limiting happen in SQL, which test_defects_since_uses_index_and_does_not_load_full_table checks, and test_gather_new_defects_has_no_python_side_filtering confirms nothing is filtered in Python. The model therefore never sees the full history, only at most 50 new rows inside a prompt capped at 4,000 characters (test_build_rich_prompt_stays_under_4000_chars), so cost and latency stay flat as the table grows.Re-running with --since 2026-04-01T00:00:00Z (shift_run_output_since.txt) made the SQL query return new=17 of the 40 warm-tier rows, so the slice that reaches the model is 17 rows rather than the full table. The default 8-hour window in my first run (shift_run_output.txt) matched none of them (new=0). The Shift C summary text comes from the recorded response in fixtures/recorded_responses/shift_C_2026-04-30.json, not from the query.

12. **Crash recovery.** shift_monitor/recovery.py sets STALE_RESUME_THRESHOLD_MINUTES = 30 (test_threshold_constant_is_30_minutes), and decide(state, now) returns "resume" or "fresh" in three steps: no steps in the manifest means fresh, a manifest already marked complete means fresh, and otherwise it resumes only if now - last_step.ts <= timedelta(minutes=30). The truth-table tests in pytest_S4.log pin this down: [29-False-resume] and [30-False-resume] resume, [31-False-fresh] is stale, and [1-True-fresh] and [60-True-fresh] show a completed run starts fresh at any age (test_recovery_decide_empty_manifest_is_fresh covers the empty case). Resuming trusts partial state that may be stale or half-written: test_mid_write_read_reveals_prior_complete_lines shows a crash can leave a partial last line in the scratchpad. A fresh start with an injected summary (test_resumed_prompt_has_both_sections) gives the model a clean, bounded context rebuilt from durable state, which is more reliable than continuing from a scratchpad that may be out of date. 
12b. **Fork isolation.** shift_monitor/fork.py: fork_for_hypothesis(base_hot_state_path, hypothesis_id, forks_root) creates forks_root/<hypothesis_id>/, copies the base hot_state.json into it with shutil.copyfile, and returns that directory. The investigation then reads and writes only its own copy, so the main hot_state.json is never mutated (test_fork_for_hypothesis_copies_state_without_mutating_base), and each fork keeps its own scratchpad file, so two forks produce independent scratchpads with no cross-contamination (test_two_forks_produce_independent_scratchpads). merge_findings(scratchpad_paths, main_scratchpad) brings results back by reading each fork's scratchpad (skipping any that don't exist) and calling main.append(entry) for each entry. It only appends and never rewrites, so earlier history in the main scratchpad is untouched (test_merge_findings_appends_without_rewriting_existing), and an abandoned or crashed fork leaves the main state unchanged. The docstring notes that the SDK-level fork_session primitive lives at Layer 2, and this module reproduces its semantics with state-file copies.
